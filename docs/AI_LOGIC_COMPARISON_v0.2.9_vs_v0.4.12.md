# HPClaw 0.2.9 与 0.4.12 AI 逻辑对比

评审日期：2026-09-21

## 取证范围

- 旧版来源：`release/HPClaw-Setup-0.2.9-x64.exe`，只读解出 `resources/app.asar`。
- 旧版 `app.asar` 可列目录并提取应用主体；安装包内两个 ARM64 conpty 附属文件损坏，不影响本次 TypeScript bundle、前端 bundle、配置和提示词取证。
- 旧版 `dist-electron/server.cjs` SHA-256：`95AF2C7312B47262BBFCF6B3086EF542FF6C3137DA133F06270A84B4ACC2F98C`。
- 当前源码版本：0.4.12。

## 结论

0.2.9 的模型、dsh 主版本、上下文窗口和摘要算法并不比 0.4.12 更强。用户感知到的“旧版更会记”主要来自旧版把 dsh 会话直接绑定到 SSH session：同一集群连接下的不同对话会共享历史。这增加了连续感，也会造成跨对话串线和隐私/任务污染。

0.4.12 已把 dsh 映射改为 `SSH session + conversation context`，对话隔离正确；但补偿机制没有同步增强，仍只保存最近 8 条、约 480 字摘要，因此隔离后暴露了长期记忆不足的问题。

正确方向不是恢复跨对话共享，而是在每个对话内部恢复足够强的结构化记忆。

## 逐项对比

| 项目 | 0.2.9 | 修改前的 0.4.12 | 本次处理 |
|---|---|---|---|
| dsh 会话映射 | `conversationKey = SSH sessionId`，不同聊天可能串线 | SSH session + conversation context，对话隔离 | 保留隔离，不回退 |
| 前端历史传输 | 最近 18 条、总计 20,000 字符 | 相同 | 提升到最近 32 条、总计 48,000 字符；服务端仍按模型预算裁剪 |
| 会话摘要 | 最近 8 条、约 480 字；memory 约 900 字 | 相同 | 目标 + 最近进展摘要约 1,200 字，长期记忆约 2,400 字 |
| 结构化记忆 | 类型和压缩器存在，但主链路未接入 | 相同 | 保存并注入任务、路径/作业号、决策、技能、错误与进度 |
| 原生 Agent 提示 | 已有计划/执行/验证规则 | 规则更多，但质量标准分散 | 增加统一的结果、成功标准、证据、恢复和停止条件契约 |
| dsh 提示 | 语言、文件展示、短摘要 | 基本相同 | 同样注入质量契约和隔离对话记忆，并标记为仅参考上下文 |
| Skill 范围 | dsh 主要装载应用 Skill | 当前还包含用户和 LSF Skill，覆盖更强 | 结构化记忆的技能提示接入检索，不恢复旧版较窄范围 |
| dsh 版本 | `0.1.0-rc.7` | `0.1.0-rc.7` | 无需降级 |
| 默认 DeepSeek 模型列表 | `deepseek-v4-pro` 优先 | 相同 | 无需恢复 |

## 本次代码改动

1. `server/ai/conversationMemory.ts`
   - 从完整对话提取原始目标、近期进展、高信号路径、作业号、参数/偏好、结果与错误。
   - 生成并持续合并 `StructuredMemory`，新事实优先保留，避免长对话后冻结在旧状态。
   - 扩充 Skill hint 的常见 HPC/生信工具识别。

2. `server.ts`
   - AI 请求按 `conversationId` 从本地权威对话库恢复该对话自己的长期记忆。
   - 原生 Agent、无集群本地 Agent 和 dsh Agent 使用同一份隔离记忆。
   - 旧对话没有结构化字段时读取即动态补齐，无需迁移脚本。

3. `server/ai/agentQualityPolicy.ts`
   - 统一定义目标、成功标准、证据、合理假设、错误恢复、停止条件和结果优先汇报方式。
   - 注入 `contextBuilder`、原生 Agent prompt 和 dsh 每轮 prompt。

4. `src/services/chatFlow.ts`
   - 扩大连续传输窗口；继续过滤隐藏计划噪音并截断单条超长工具输出。

## 未采用的“恢复”方式

- 不恢复跨对话共用 dsh history。它会让 A 对话中的样本路径、作业号和结论进入 B 对话。
- 不降级 dsh 或模型版本。两版实际相同，降级不能解释强度差异。
- 不取消命令审批、路径边界和作业 watcher。这些机制不降低推理质量，反而保证 Agent 可验证、可恢复。

## 后续建议

1. 建立固定 Agent 回归集，至少覆盖：长对话参数保持、Skill 选择、失败恢复、作业提交后续跑、对话隔离和新旧版本盲测。
2. 为界面增加“本轮使用的记忆 / Skill / 引擎”折叠面板，便于判断回答差是模型、上下文还是工具选择导致。
3. 统计每轮工具调用、重复调用、摘要命中和完成证据，形成可比较 trace；不要只以单元测试通过判断 Agent 强度。
