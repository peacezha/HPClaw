# HPClaw：面向生物信息学高性能计算集群的智能操作工作台

# HPClaw: An Intelligent Workspace for Bioinformatics High-performance Computing Clusters

## 摘要

生物信息学分析通常运行在配备作业调度器、模块系统和共享存储的高性能计算集群上。研究人员需要同时处理命令行操作、软件环境、资源申请、远程文件、作业日志和结果检查。现有工作流系统能够提高流程的可复现性，但用户在分析前后的环境探查、异常处理和结果查看环节仍常常依赖独立的 SSH 客户端、文件工具和人工查阅集群规范。大语言模型可以生成命令并解释日志，但在无法访问实时集群状态时，生成内容容易建立在不完整或错误的环境假设之上。

本文介绍 HPClaw，一个将 Web SSH 终端、AI Agent、LSF 作业管理、远程文件操作和生物信息学知识组织在同一会话中的软件系统。系统通过 OpenSSH 建立真实的远程会话，以结构化集群状态快照描述当前路径、文件、作业、配额和模块环境；通过文件类型识别器推断目录所处的分析阶段；通过技能索引和技能关系图谱选择与任务相关的操作知识；通过结构化记忆和观测记录保存长任务中的事实、决策、错误和状态变化。Agent 只通过受控工具与集群交互，并设置命令预算、步骤上限、连续失败停止、重复命令停止和危险删除拦截。前端将终端输出、作业状态、日志、代码、表格和生物信息学文件预览集中呈现。

当前版本已通过 31 个测试文件中的 95 个测试、TypeScript 类型检查和 Vite 生产构建。上述结果说明主要模块能够完成预期的工程级接口和行为检查，但不等同于任务效率、用户可用性或跨集群泛化能力的实验结论。HPClaw 的适用范围目前以 NCPGR/LSF 类环境为主，生产部署仍需要进一步完善权限隔离、操作审计和跨调度器验证。

关键词：生物信息学；高性能计算；智能体；SSH；LSF；工作流管理；远程文件；可追溯操作

## 1 引言

测序数据处理、转录组定量、变异检测和群体遗传分析通常需要在高性能计算集群上运行。与本地工作站相比，集群能够提供共享存储、批处理队列和可扩展的计算资源，但任务的执行过程也更依赖环境细节。研究人员需要确认输入文件、参考序列、软件版本、线程数、输出目录和日志位置，还需要遵循模块系统、队列策略、资源限制以及机构制定的运行规范。任何一个环节的信息缺失，都可能使任务在错误的目录、错误的计算节点或不合适的资源配置下运行。

现有生物信息学工作流系统已经解决了部分流程组织问题。Galaxy 通过图形化界面和可复用工具封装降低了分析入口的使用门槛[1]；Nextflow 和 Snakemake 分别从流程描述、依赖管理和可复现执行等角度支持复杂分析[2,3]；Bioconda 则为软件分发和环境配置提供了统一渠道[4]。这些系统的共同特点是把分析流程定义为可重复执行的程序或任务图。相比之下，集群上的交互式问题定位仍包含大量流程外操作，例如查看当前目录、确认文件命名、检查队列状态、阅读失败日志、选择模块版本以及判断上一次会话留下的中间结果。此类操作通常发生在多个工具之间，难以由一个工作流文件完整描述。

大语言模型为这类交互提供了自然语言入口。用户可以直接描述分析目标，模型也可以根据日志生成解释或给出命令。但是，通用对话模型通常无法直接获知当前远程会话的工作目录、文件集合、作业状态、配额和模块环境。当模型根据默认环境生成命令时，错误可能不是语法错误，而是路径、样本、参考基因组或调度器规则不匹配。对于需要提交长时间作业或修改远程文件的任务，模型还需要在自动执行速度和人工确认之间保持明确边界。

HPClaw 针对上述交互断层设计了一个面向生物信息学集群的操作工作台。其基本思路是把自然语言请求放入一个可观察的远程任务状态中：Agent 在行动前读取集群事实，依据任务需要检索技能知识，在缺少关键参数时向用户确认，并将命令、输出、作业和文件变化写入会话记录。本文的贡献包括三点。第一，给出一个将 Web SSH、LSF 作业控制和 AI 工具调用连接起来的远程操作架构。第二，给出一种由集群状态、文件类型、技能关系、任务计划和结构化记忆共同构成的上下文组织方法。第三，给出一组面向真实远程操作的执行约束和工程验证结果，并明确系统尚未被当前证据支持的性能和泛化结论。

## 2 相关工作与问题定义

### 2.1 工作流系统与交互式集群操作

Galaxy、Nextflow 和 Snakemake 分别代表图形化分析平台、流程编排系统和规则驱动的工作流引擎。它们适合表达明确的输入、步骤和输出，并能通过流程文件、软件环境或运行记录改善可复现性[1-4]。然而，生信任务并不总是从一个完整且稳定的流程文件开始。实际分析往往先从一个目录和一段自然语言目标开始，用户需要根据文件内容决定下一步，并在任务失败后回到环境探查和日志诊断。HPClaw 的定位不是替代这些工作流系统，而是补充流程定义之前和流程运行过程中的交互操作。对于需要重复运行的正式分析，HPClaw 可以生成或提交 LSF 脚本；对于一次性的环境检查、错误定位和结果查看，系统提供与远程状态相连的交互入口。

### 2.2 任务定义

对每个任务，系统同时接收用户请求、远程集群观测、任务相关技能和会话记忆。集群观测包括当前路径、文件列表、作业状态、配额和模块信息；会话记忆包括任务进度、关键事实和错误记录。Agent 据此生成自然语言回复，或选择一个受控工具动作。动作执行后，系统获取新的远程观测，并更新任务记忆和观测记录。系统的作用不是替用户决定完整的生物学分析方案，而是把每一个需要落地到远程环境的动作置于可检查的状态和知识范围内。

本文将 HPClaw 的问题范围限定为三类操作：远程环境探查，包含目录、文件、模块、队列和配额检查；分析任务执行，包含命令运行、LSF 脚本生成和作业提交；任务结果处理，包含日志解释、文件预览、状态汇报和会话恢复。本文不把 HPClaw 描述为自动完成所有生物信息学分析的通用系统，也不据此推断其对实验设计或生物学结论的替代能力。

## 3 系统架构

HPClaw 由前端工作台、会话与远程执行层、Agent 与知识层以及持久化层组成。前端采用 React 和 xterm.js，后端采用 TypeScript、Express 和 Socket.IO；AI 对话和 Agent 工具结果通过服务器发送事件返回。远程端保持用户原有的 SSH 和 LSF 工作环境，系统主要负责建立会话、获取状态、执行受控操作以及整理结果（图 1）。

### 3.1 Web/Electron 工作台

用户通过浏览器或 Electron 入口登录远程集群。工作台将 AI 对话、终端、文件管理、技能检索和会话历史放在同一登录上下文中。终端中的选中文本可以直接发送给 AI 进行错误解释或命令分析，远程文件可以在文件面板中浏览，并根据类型进入代码、表格、图像、序列或日志预览。该布局解决的是信息切换问题：模型看到的终端片段、用户当前查看的文件和实际 SSH 会话属于同一个工作空间，而不是相互独立的复制粘贴对象。

### 3.2 SSH 会话与远程执行

终端会话由服务端启动 OpenSSH 子进程并分配伪终端，Socket.IO 负责在浏览器和远程会话之间转发输入输出。登录模块支持密码和动态验证码，并通过 `SSH_ASKPASS` 机制向 OpenSSH 提供认证信息。会话对象维护命令队列，使 AI 命令、文件读取和其他远程操作按顺序执行，避免多个请求同时写入同一个伪终端。

命令执行需要区分终端显示和程序化结果。HPClaw 在命令前后写入随机标记，根据标记提取本次命令的输出，并在需要时暂时关闭终端回显。超过执行时间后，系统向远程会话发送中断信号并恢复回显状态。小文件可通过终端通道读取，较大的文件采用非交互 SSH 传输，以减少二进制数据混入终端输出的风险。文件预览设置大小和数量上限，避免把完整大文件直接载入浏览器或模型上下文。

### 3.3 集群状态快照与文件识别

Agent 不能仅依据用户的描述决定下一步操作。HPClaw 提供 quick、standard 和 full 三档集群快照。quick 快照读取当前路径和目录文件，standard 快照增加 LSF 作业和配额信息，full 快照进一步读取递归文件、队列和模块信息。快照被整理为包含 `workingDir`、`files`、`jobs`、`quota`、`modules`、`queueStatus` 和时间戳的结构化对象。

目录文件随后由 `FileRecognizer` 进行类型和阶段识别。识别规则覆盖 FASTQ、FASTA、BAM、SAM、VCF/GVCF、BED、GFF/GTF、LSF、CSV/TSV、图像、PDF 以及 R、Python 脚本等常见类型。文件名和组合关系可以生成有限的阶段提示，例如将 FASTQ 识别为原始测序数据，将 BAM 和索引文件识别为比对后的数据，将 VCF 或 GVCF 识别为变异检测相关结果。该识别结果只作为上下文提示，不直接替代用户对样本、物种和参考文件的确认。

### 3.4 技能索引与上下文编排

HPClaw 将领域知识保存为可检索的技能文件。技能来源包括系统内置技能、LSF/NCPGR 集群规范、用户技能目录和远程集群中的 `~/hpclaw_skills`。索引器支持 Markdown、YAML、JSON、Shell、Python、R、LSF、CSV/TSV 和日志等文本内容，并统一记录技能名称、标签、来源和正文。

单纯按关键词拼接全部技能会造成上下文过长，也会把不适用的集群规则混入当前任务。因此，系统为技能建立关系图谱，从 frontmatter 中读取 `depends_on`、`related_to`、`used_with` 和 `solves` 等关系。编排器首先根据用户请求、文件类型和任务计划选取入口技能，再扩展必要的依赖和相关技能，并按 token 预算裁剪知识包。LSF/NCPGR 规范以可单独选择的手册分片进入上下文。最终送入 Agent 的内容由用户请求、集群状态、技能、记忆、观测和对话历史构成，而不是完整复制技能库。

### 3.5 Agent 工具循环与执行约束

Agent 通过四类工具与工作台交互：`run_command` 执行单条远程命令，`search_skills` 检索技能，`ask_user` 请求缺失参数或确认不确定操作，`save_skill` 将经过整理的经验或脚本保存为技能。服务端使用 SSE 返回回复、工具调用、工具结果、步骤和结束状态，因此用户可以看到当前动作已经进入执行、等待确认还是发生错误。

当前实现对执行循环设置了明确的边界：单次任务最多 50 个 Agent step，最多 40 次 `run_command`；连续 3 次命令失败后停止；同一命令重复到第 3 次时停止；直接使用 `rm` 的命令被拒绝，系统提示使用移动到临时目录等可恢复方式。对于预计运行时间较长的生信任务，提示规则要求通过 `bsub` 提交，而不是在登录节点直接运行。上述约束属于工程守卫和默认策略，不构成对所有风险的形式化证明。高风险操作还需要结合路径权限、用户确认和部署环境进行审计。

NCPGR/LSF 规则被作为集群相关知识注入系统，包括计算节点网络限制、长任务使用 `bsub`、LSF 脚本后缀、单节点并行约束、线程数环境变量以及模块查询顺序。该设计使同一 Agent 的执行行为可以随集群规则包变化，而不必把所有机构规范写死在通用提示中。

### 3.6 记忆、观测和结果呈现

长周期生信任务需要保存的不只是聊天文本。HPClaw 的结构化记忆包含任务目标、进度、关键事实、决策、已使用技能和错误历史。记忆编排器在对话增长或上下文接近预算上限时生成摘要，同时保留后续执行所需的路径、样本、参考文件和参数。观测存储记录命令、输出、错误、警告、状态变化、作业提交和文件创建等事件，并按重要性保留信息。

对话存档以 JSON 文件写入远程用户目录，允许用户在不同浏览器会话或后续工作日恢复任务。前端对代码、表格、图像、FASTA/FASTQ 和普通文本使用不同的富内容组件，结果查看不再完全依赖复制路径和切换外部软件。该层的目标是保留工作过程和结果之间的联系，而不是替用户解释所有生物学结果。

## 4 代表性工作流

### 4.1 从 FASTQ 目录到质控任务

用户可以在当前目录提出“对这些 FASTQ 文件进行质控”之类的请求。Agent 首先通过 `run_command` 获取工作目录和文件列表，再调用 `search_skills` 检索质控工具和当前集群的提交规范。若目录中包含成对文件，文件识别结果可提示双端测序的可能性；若缺少样本命名、输出目录或软件版本等信息，Agent 通过 `ask_user` 询问，而不是直接生成提交命令。

在参数足够且任务预计运行时间较长时，Agent 生成 LSF 脚本，写入输入路径、线程数、日志路径和输出目录，并通过 `bsub` 提交。提交后的作业编号和 `bjobs` 状态被写入观测记录。任务完成后，用户可以在同一工作台查看日志、输出文件和质量控制报告。该流程展示了 HPClaw 的重点：自然语言只负责表达目标，执行仍然需要经过环境探查、参数确认和调度器约束。

### 4.2 作业状态和错误处理

如果作业处于 `PEND`、`RUN` 或 `EXIT` 状态，Agent 可以根据 LSF 输出解释队列等待、资源不足、路径错误、模块缺失或程序返回码。解释内容与原始命令和日志片段一起保存，用户可以继续追问或直接在终端中修正。连续失败保护用于终止无效的重复尝试，但不会自动判断失败的生物学原因；当错误涉及参考基因组、样本对应关系或输出覆盖时，仍需用户作出决定。

### 4.3 结果浏览和技能沉淀

任务产生的表格、图像、代码、序列和日志可以通过文件面板查看。用户确认某个脚本或排错过程具有复用价值后，可以将其保存为技能，后续任务再通过关键词、标签和关系图谱检索。技能沉淀把一次操作中的局部经验转化为可复用的知识文件，但技能的版本、来源和适用集群仍需要由维护者负责。

## 5 工程验证

### 5.1 测试与构建

本文报告的是当前代码版本的工程验证，而非任务效率或用户实验。测试套件包含 31 个测试文件，共 95 个测试，覆盖 Agent 的用户追问、重复命令和超时停止，以及集群技能扫描、文件识别、上下文构建、记忆和远程操作等模块。`npm run lint` 通过 TypeScript 类型检查，`npm run build` 完成 Vite 生产构建并转换 2,138 个模块。

生产构建同时提示主 JavaScript chunk 约为 796.83 kB，gzip 后约为 229.77 kB，超过 Vite 默认的 500 kB 警戒线。这一结果不影响构建完成，但说明前端仍可通过动态导入或 `manualChunks` 进行拆分。服务端主入口和 AI 对话组件的职责较为集中，也提示后续需要进一步模块化。将这些工程问题写入验证结果，有助于区分“功能可运行”和“已经适合大规模部署”这两个不同结论。

### 5.2 可复现运行条件

系统运行需要 Node.js 18 或更高版本、可用的 OpenSSH 客户端和远程 HPC 账号；AI 功能还需要配置至少一个兼容的模型服务端点。当前项目采用 TypeScript、Express、Socket.IO、React、xterm.js、Vite 和 Vitest。代码仓库和许可证信息见参考文献[5]。正式投稿时，应将提交所使用的代码版本、集群规则包、测试脚本和配置文件一并归档，并记录依赖版本和模型服务端点。

### 5.3 评价范围与限制

现有测试能够验证模块接口、边界条件和部分安全策略，但不能回答以下问题：HPClaw 是否比传统 SSH 操作更快，是否减少了命令错误，用户是否承担了更低的认知负担，以及系统在不同调度器和不同集群规则下是否保持稳定。后续评价应在固定任务集上比较传统 SSH、带通用聊天模型的 Web SSH 和 HPClaw，并记录任务成功率、完成时间、命令数量、人工干预次数、失败类型、作业提交正确性和用户负担。任务集还应包括缺失参数、路径冲突、模块不可用、队列等待和大文件传输等压力场景。

## 6 讨论

HPClaw 的主要贡献不在于增加一个聊天入口，而在于把聊天请求放回真实的远程状态中。对于集群任务，命令是否合理取决于当前目录、文件结构、模块环境、队列规则和作业历史。集群快照、文件识别、技能编排和结构化记忆共同提供了这些条件，使 Agent 的动作可以与可观察事实关联。该设计与 Galaxy、Nextflow 和 Snakemake 的关系是互补的：工作流系统负责稳定流程的表达和重复执行，HPClaw 负责流程开始前的环境判断、执行过程中的交互排错以及结果返回后的文件检查。

技能图谱的作用也需要限定。它可以组织依赖关系和适用场景，减少把全量知识放入上下文的需要，但当前实现主要依赖文本索引、标签和显式关系，并不能保证每次检索都得到最优技能。技能内容本身可能过期，特别是软件版本、队列配置和机构规则发生变化时，维护者需要重新审核。因而，知识检索应当被视为一种上下文选择机制，而不是对领域知识正确性的替代验证。

安全策略同样具有明确边界。命令预算、重复检测和 `rm` 拦截能够处理一部分常见错误模式，但它们不能覆盖路径转义、权限配置、恶意技能内容、凭证泄露、多用户隔离和数据外传等生产风险。当前文件删除接口仍需要结合部署环境实施更严格的路径校验、权限控制、审计日志和可恢复机制。对于涉及样本隐私或受限数据的集群，还需要将认证、会话存储、模型服务商和日志保留策略纳入机构级安全评估。

最后，HPClaw 当前的集群规则主要围绕 NCPGR/LSF 组织。其上下文和技能接口为扩展 Slurm、PBS 等调度器提供了结构，但接口可扩展并不等于跨集群行为已经得到验证。后续工作应优先完成多集群适配和任务级对照实验，再讨论效率、可靠性或泛化能力。只有在这些证据建立后，系统才适合被描述为面向更广泛 HPC 场景的通用工具。

## 7 结论

HPClaw 将 Web SSH、LSF 作业管理、集群状态快照、技能知识、结构化记忆和富内容结果呈现组织为一个面向生物信息学集群的智能操作工作台。其核心设计是让 Agent 在真实环境事实和本地规则约束下执行单条远程操作，并在关键参数缺失或风险较高时保留用户确认环节。当前代码已经通过测试、类型检查和生产构建，证明系统具备可运行的工程基础；这些结果尚不足以证明其能够提高任务效率或降低用户负担。HPClaw 下一步需要通过固定任务、明确基线、真实用户和多集群部署来检验其实际价值，同时完善权限、审计和数据保护机制。
