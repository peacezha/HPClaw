# HPClaw：面向生物信息学 HPC 集群的智能 Web 操作平台

作者：待补充

单位：待补充

通讯作者：待补充

版本：论文草稿 v0.1

## 摘要

生物信息学分析通常依赖高性能计算（High Performance Computing, HPC）集群、作业调度系统、命令行软件、文件传输工具和大量领域经验。对于许多实验研究人员而言，从科研问题到可执行命令之间仍存在明显断层：研究者需要在聊天沟通、终端操作、远程文件管理、脚本编写、LSF 作业提交、错误排查和结果解读之间频繁切换。本文介绍 HPClaw，一个面向生物信息学 HPC 集群的智能化 Web 操作平台。HPClaw 将 SSH Web 终端、AI Agent、远程文件管理、LSF 作业控制、领域技能知识库、集群状态感知和会话记忆整合到统一浏览器界面中，使用户能够用自然语言描述分析目标，并由系统在真实集群环境中执行只读探查、技能检索、命令生成、作业提交、文件读取与结果解释等操作。

HPClaw 的核心设计是将浏览器会话视为一个持续的集群工作空间。系统通过 Express 与 Socket.IO 维护 SSH 交互，通过 Server-Sent Events 流式返回 AI 推理和执行过程，通过技能图谱和文件类型识别将 FASTQ、BAM、VCF、FASTA、LSF 脚本等生物信息学文件映射到相关技能，并通过结构化记忆、观测记录和 token 预算管理维持长对话上下文。与仅提供问答或命令建议的助手不同，HPClaw 强调工具落地与集群约束：AI 在执行前读取真实工作目录、作业状态和磁盘配额；对长时间计算任务遵循 LSF 调度规范；在样本路径、参考基因组、物种、链特异性或长作业提交存在不确定性时触发“先问再做”机制。本文描述 HPClaw 的系统架构、Agent 执行循环、技能编排机制、远程文件和会话管理实现，并讨论其在 RNA-seq 质控、作业监控、文件预览、错误解释和集群知识沉淀中的应用潜力。现阶段仍需补充系统化基准实验、真实用户研究和跨集群部署评估。

关键词：生物信息学；高性能计算；HPC；AI Agent；Web 终端；LSF；技能知识库；人机协作

## 1 引言

现代生物医学研究高度依赖计算分析。测序质控、比对、变异检测、转录组定量、差异表达分析、富集分析和可视化等流程通常运行在 HPC 集群上。这类环境具备强大的计算能力，但也带来显著使用门槛：用户需要理解 Linux 命令、模块系统、队列资源、脚本格式、文件路径、软件参数、作业日志以及常见错误。尤其在采用 LSF 等调度系统的共享集群中，研究者不仅要知道“运行什么工具”，还要知道“何时在登录节点执行”“何时提交到计算节点”“申请多少核心”“如何查看排队原因”“如何避免计算节点无网络导致下载失败”等集群本地规范。

近年来，大语言模型和工具调用型智能体为科研计算提供了新的交互范式。用户可以用自然语言描述目标，模型再生成命令、解释错误或调用外部工具。然而，在真实 HPC 生物信息学环境中，通用 AI 助手仍面临三类问题。第一，环境不可见。模型若无法读取真实目录、模块、作业和配额，容易基于假设生成命令。第二，知识碎片化。分析流程需要结合软件说明、集群规范、实验设计和历史上下文，单次提示难以覆盖完整信息。第三，执行风险较高。错误路径、错误物种、错误参考基因组或盲目提交长作业，可能浪费大量集群资源并造成数据混乱。

为降低这些障碍，本文提出 HPClaw。该系统不是将 AI 聊天窗口简单嵌入终端旁边，而是把 Web 终端、SSH 会话、AI 工具调用、文件管理、技能知识库和集群会话持久化组织为一个统一工作台。HPClaw 面向的核心场景是：研究人员在浏览器中登录 HPC 集群，查看当前目录和文件，向 AI 描述任务，AI 结合实时集群状态和生物信息学技能库进行规划，并通过受控工具调用执行命令、检索技能、保存知识或向用户追问关键参数。

参考 BioClaw 一文关于“将自然语言科研请求转化为可执行工作流”的系统论文写法，本文将 HPClaw 定位为面向 HPC 集群而非群聊平台的智能执行环境。两者共享的思想是：科研协作不应停留在文本回复，而应连接真实工具和可复用工作空间。HPClaw 的差异在于，其执行场所是用户已有的 HPC 集群，重点解决 SSH 交互、集群规则、LSF 调度、远程文件、会话恢复和生物信息学技能注入等问题。

本文的主要贡献如下：

1. 提出一个面向生物信息学 HPC 集群的智能 Web 工作台，将 SSH 终端、AI Agent、远程文件管理、LSF 规则、技能知识库和会话记忆整合在同一浏览器界面中。
2. 设计并实现一种集群感知的 Agent 上下文构建流程，通过实时目录快照、作业状态、磁盘配额、文件类型识别和技能图谱检索，使 AI 决策建立在真实集群状态之上。
3. 构建技能知识库和技能编排机制，将本地技能、LSF/NCPGR 集群规范、用户技能和远程集群技能合并索引，并根据用户问题、文件类型、任务计划和记忆事实动态生成知识包。
4. 实现一个面向真实 SSH 会话的工具执行层，支持命令运行、技能搜索、技能保存、用户追问、流式响应、远程文件浏览与传输、对话存档和富内容展示。
5. 总结系统当前局限，并给出后续评估所需的性能、可靠性和用户研究指标。

## 2 系统目标

HPClaw 的总体目标是让 HPC 集群会话本身成为生物信息学分析的智能工作空间，而不是让 AI 只充当外部问答工具。形式化地，对于每个登录用户会话 \(S\)，系统维护：

\[
C_S = (T_S, F_S, A_S, K_S, M_S, O_S)
\]

其中 \(T_S\) 表示 SSH 终端状态，\(F_S\) 表示远程文件和工作目录，\(A_S\) 表示正在运行或待运行的分析动作，\(K_S\) 表示技能知识包，\(M_S\) 表示会话记忆，\(O_S\) 表示命令、错误、文件和作业相关观测。给定用户的新请求 \(P_t\)，HPClaw 将 \((P_t, C_S)\) 映射为一组可执行或可交互动作：

\[
(P_t, C_S) \rightarrow (R_t, Q_t, U_t, C_{S}^{\prime})
\]

其中 \(R_t\) 是 AI 生成的自然语言解释，\(Q_t\) 是在集群中执行的命令或工具调用，\(U_t\) 是返回给用户的文件、表格、图像或状态摘要，\(C_{S}^{\prime}\) 是更新后的会话上下文。该目标包含三项约束。

第一，系统必须持久。生物信息学任务往往跨越多个步骤和多个工作日，用户需要能够恢复此前对话、文件位置、分析决策和错误历史。第二，系统必须工具落地。模型负责规划、解释和选择工具，但关键事实必须来自 SSH 命令、文件内容、作业系统和技能库，而不是模型记忆。第三，系统必须遵守集群规范。对于 NCPGR/LSF 场景，HPClaw 内置“计算节点无互联网”“长任务使用 bsub”“脚本使用 .lsf 后缀”“通过 module av/module load 查询软件”等约束，减少错误提交和资源浪费。

## 3 系统总体架构

HPClaw 采用 TypeScript 全栈实现。后端基于 Express、Socket.IO 和 Server-Sent Events，前端基于 React 19、Vite、Tailwind CSS 和 xterm.js。系统由六个主要层次组成。

### 3.1 Web 交互层

前端提供登录页、终端主界面、AI 聊天侧栏、右侧文件/历史面板、技能面板、命令补全浮层和终端文本浮动工具栏。用户登录后，中心区域为 xterm.js 终端；左侧为 AI Chat，可在“深度思考”和“快速思考”之间切换；右侧可打开远程文件管理器或对话历史。用户在终端中选中文本后，可以一键发送给 AI 解读或分析错误。

### 3.2 SSH 会话层

后端通过 OpenSSH 子进程建立真实 SSH 会话。登录接口接收 host、port、username、password 和 Google Authenticator 验证码，并通过 SSH_ASKPASS 机制向 SSH 进程提供密码和动态验证码。Socket.IO 将浏览器终端输入输出与 SSH 进程标准流连接起来，实现实时交互。系统为每个登录会话维护 sessionId、主 SSH 进程、控制路径、临时凭证文件、输出缓冲和命令队列。

### 3.3 AI 网关层

AI 网关支持 DeepSeek、OpenAI、Google Gemini、Grok、Moonshot/Kimi 以及自定义 OpenAI 兼容端点。前端可以在本地保存 provider、model、apiKey 和 baseUrl 配置。普通聊天可通过非流式接口完成，Agent 模式通过 `/api/ai/stream` 使用 SSE 持续返回文本、推理、工具调用、工具结果、步骤编号、追问和完成事件。

### 3.4 Agent 工具执行层

Agent 通过受控工具与集群交互，主要工具包括：

- `run_command`：在当前 SSH 会话中执行单条 shell 命令并返回输出。
- `search_skills`：检索本地、LSF 和集群技能知识库。
- `save_skill`：将有价值的脚本或经验保存为技能。
- `ask_user`：在关键参数缺失或操作风险较高时向用户追问。

系统要求 Agent 在生物信息学任务前先检索技能，执行前读取真实集群状态，长时间计算使用 bsub，禁止直接执行危险删除命令，并在提交作业后返回作业 ID 和监控建议。

### 3.5 技能知识层

HPClaw 的技能知识层包含本地技能、导入技能、LSF 集群技能和远程集群技能。技能文件可以是 Markdown，也可以是常见文本脚本格式。系统通过 frontmatter、文件名、标签、描述和正文建立技能索引，并通过技能图谱建模 `depends_on`、`related_to`、`used_with` 和 `solves` 等关系。对于远程集群技能，HPClaw 会扫描用户家目录下的 `~/hpclaw_skills`，将文本类技能文件作为会话级知识注入，而不写入本地 `skills/` 目录。

### 3.6 记忆与观测层

系统将对话、结构化记忆、终端观测和集群快照作为上下文来源。对话会以 JSON 文件形式保存到远程集群 `$HOME/hpclaw_conversations/` 目录，便于跨浏览器或跨会话恢复。结构化记忆记录任务、阶段进度、关键事实、分析决策、使用过的技能和错误解决历史。观测存储记录命令、输出、错误、警告、作业提交和文件创建等事件，用于后续 AI 推理。

## 4 集群感知上下文构建

HPClaw 的关键特点是 AI 在回答或执行前能够读取集群状态。系统中的 `ClusterContextProvider` 定义了 quick、standard 和 full 三类快照命令。quick 快照采集当前路径和目录文件；standard 快照进一步采集 `bjobs -w` 和 `quota -s`；full 快照增加递归目录、队列、模块和配额信息。采集结果被解析为 `ClusterSnapshot`，包含 workingDir、files、jobs、quota、modules、queueStatus 和 timestamp。

文件列表不是简单文本，而会通过 `FileRecognizer` 进行类型识别。系统内置 FASTQ、BAM、SAM、VCF、GVCF、BED、GFF/GTF、FASTA、LSF、Shell、CSV/TSV、图片、PDF、R 脚本和 Python 脚本等规则。例如，`.fastq.gz` 会映射到 `qc` 和 `fastp` 技能，`.bam` 会映射到 `alignment` 和 `formats` 技能，`.lsf` 会映射到 `lsf-ncpgr` 技能。系统还会根据目录中文件组合推断分析阶段：只有 FASTQ 时可判断为“原始数据阶段（待质控）”，FASTQ 与 HTML 报告同时存在时可判断为“质控阶段已完成”，出现 BAM 时可判断为“比对后处理阶段”，出现 VCF/GVCF 时可判断为“变异检测阶段”。

在 AI 请求进入后端时，`buildSmartContext` 会根据模型上下文窗口设置 token 预算，并依次组织以下信息：系统角色、集群快照、当前任务计划、技能知识包、结构化记忆、观测摘要、用户选中的终端输出和最近对话历史。Token 预算管理器根据模型窗口为集群上下文、技能、记忆、观测和对话历史分配空间，并预留响应 token，避免长技能库或长终端输出挤占全部上下文。

这种设计使 Agent 的输入不再只是用户自然语言请求，而是一个多源、结构化、受预算控制的上下文包。对于“帮我对当前目录 FASTQ 做质控”这类请求，模型可以在同一上下文中看到当前路径、FASTQ 文件名、已存在报告、LSF 规范、fastp/FastQC 技能摘要、历史错误和用户偏好，从而减少无效探查和错误假设。

## 5 技能图谱与知识编排

HPClaw 的技能系统借鉴了“技能即可复用操作知识”的思想，但其重点是面向 HPC 生物信息学场景进行组合检索。每个技能条目包含 filename、name、description、tags、trigger、category、content、source、sourcePath 和 relation 字段。技能来源可分为 system、imported、user、lsf 和 cluster。

技能图谱由 `SkillGraphBuilder` 从 frontmatter 中抽取关系构建。`depends_on` 关系权重最高，用于表示使用某技能前必须掌握的前置知识；`solves` 表示技能解决的问题；`used_with` 表示经常配合使用；`related_to` 表示主题相关。`SkillOrchestrator` 首先根据用户问题、集群文件提示、任务计划提示和记忆事实搜索入口技能，然后从图谱中向外扩展，按核心技能、依赖技能、相关技能和集群手册分片组织知识包。

以 RNA-seq 分析为例，用户请求可能首先命中 transcriptome 或 qc 技能；若当前目录中存在 FASTQ 文件，文件识别器会补充 qc/fastp 提示；若集群规则中要求长任务使用 LSF，lsf-ncpgr 技能会进入相关技能或 Bible 分片。最终提供给 AI 的不是全量技能库，而是受 token 预算约束的技能知识包，包含核心步骤、关键参数、LSF 模板和本地集群注意事项。

远程集群技能进一步允许用户把个人经验沉淀在 `~/hpclaw_skills` 中。系统支持 `.md`、`.txt`、`.yaml`、`.json`、`.sh`、`.py`、`.R`、`.lsf`、`.csv`、`.tsv`、`.log` 等文本格式，并限制最大文件数和最大读取字节数，防止误把大日志注入上下文。这使 HPClaw 能够逐步适应不同实验室、不同用户和不同集群的软件习惯。

## 6 Agent 执行循环与先问再做机制

HPClaw 的 Agent 模式使用 AI SDK 工具调用循环。系统提示要求模型“必须使用工具而不是凭记忆回答”，并将操作限制为单条命令执行、技能搜索、用户追问和技能保存。每次工具调用、工具结果和文本增量都通过 SSE 发回前端，用户可以实时看到 Agent 的执行过程。

在真实 HPC 环境中，“自动执行”与“安全确认”之间需要平衡。HPClaw 的设计区分了低风险探查和高影响操作。只读命令如 `pwd`、`ls`、`find`、`head`、`module av`、`bjobs`、`quota` 可以直接执行，用于获取事实；但当下一步依赖不确定、冲突或高影响假设时，Agent 必须触发 `ask_user`。必须先问的情况包括：样本名或路径无法确定，参考基因组、GTF/GFF、物种、单端/双端、链特异性等关键参数缺失，准备创建或覆盖脚本、修改文件、提交长任务时仍存在多个合理选择，或集群实际状态与用户描述冲突。

这一机制避免了两类常见错误。一类是“模型过度自信”：在不知道参考基因组或样本表时直接生成完整分析脚本。另一类是“人机协作断裂”：AI 探查后发现关键事实缺失，却继续猜测执行。HPClaw 通过 `ask_user` 将不确定性显式返回给用户，并在用户下一轮回复后继续使用此前上下文。

## 7 远程文件管理与富内容展示

生物信息学分析离不开文件查看和传输。HPClaw 的右侧文件管理器通过 SSH 命令列出远程目录，支持进入目录、返回、刷新、上传、下载、删除和创建目录。文件读取接口会先检查 MIME 类型和大小，限制单文件预览上限，并区分文本和二进制内容。下载和上传采用 base64 编解码与非 PTY SSH 子进程，避免终端回显污染。

前端富内容组件能够根据扩展名或 MIME 类型识别图像、表格、代码、FASTA/FASTQ、VCF、PDF、日志和通用文件。AI 回复中若出现文件路径，系统可以展示为卡片式内容，减少用户在终端和本地工具之间切换。对于 FASTA 类序列文件，可进一步展示序列统计；对于 CSV/TSV，可渲染为表格；对于图像结果，可直接预览。

需要注意的是，当前文件删除接口对目录使用 `rmdir`，对文件使用 `rm -f`，并阻止根路径、`/home` 和 `~` 等危险路径。后续若要部署到多人共享生产环境，仍建议进一步收紧路径白名单、审计删除操作，并加入回收站式移动而非直接删除。

## 8 会话存档、记忆和恢复

HPClaw 将对话历史存储到远程集群 `$HOME/hpclaw_conversations/`，而不是只保存在浏览器本地。每个会话以 JSON 文件保存，包含 id、title、createdAt、updatedAt、clusterInfo 和 messages。用户可以在右侧历史面板中加载旧对话，继续此前分析。

除原始消息外，系统还设计了结构化记忆。结构化记忆包含任务名称、阶段进度、关键事实、决策记录、已使用技能和错误解决记录。例如，在一次 RNA-seq 分析中，记忆可以记录“参考基因组为 hg38”“用户偏好 STAR 而非 HISAT2”“100 个双端 FASTQ 文件位于某目录”“上次 fastp 作业因模块未加载失败”等信息。相比简单截断历史消息，结构化记忆更适合长任务恢复和跨阶段推理。

观测存储则记录命令、输出、错误、状态变化、作业提交和文件创建等事件，并为每条观测标注重要性、相关技能和相关文件。这些信息在后续请求中以摘要形式注入上下文，使 AI 能够基于真实操作轨迹继续工作。

## 9 代表性应用场景

本文根据项目功能总结 HPClaw 的代表性使用场景。以下案例为功能层面的设计与代码支持场景，尚需补充真实运行截图、任务数据和定量评估。

### 9.1 当前目录 FASTQ 质控

用户在终端进入包含 FASTQ 文件的目录后，可向 AI 输入“对当前目录的 FASTQ 文件做质控分析”。Agent 首先执行只读探查，读取 `pwd`、`ls -lh`、`module av fastqc` 或相关命令，结合文件识别器判断当前处于原始数据阶段，并检索 qc/fastp/LSF 技能。若样本命名清晰且用户允许执行，系统可生成 LSF 脚本并提交；若链特异性、样本表或输出目录存在不确定性，则向用户追问。

### 9.2 LSF 作业提交与监控

对于预计超过 2 分钟的计算任务，HPClaw 内置规则要求通过 bsub 提交到计算节点。Agent 会根据 NCPGR 规则建议 `.lsf` 脚本、`span[hosts=1]`、`$LSB_DJOB_NUMPROC`、队列选择和核心数。提交后，系统返回作业 ID，并可通过 `bjobs`、`bhist` 或 `bpeek` 查看状态和日志。

### 9.3 终端错误解释

用户在终端中选中报错文本后，可通过浮动工具栏发送给 AI。AI 分析模块会结合当前 HPC 场景解释错误原因，并给出具体下一步，如检查 module、确认路径、查看日志、减少核心数、检查文件格式或重新提交作业。相比直接复制到通用聊天工具，HPClaw 可利用会话上下文和集群技能给出更贴近本地环境的建议。

### 9.4 远程结果预览与下载

分析生成的 HTML、PNG、CSV、TSV、FASTA 或日志文件可以在文件管理器中浏览、预览或下载。AI 回复中的结果路径也能被识别为富内容卡片。该设计降低了用户通过 scp、sftp 或手动路径复制查看结果的成本。

### 9.5 集群知识沉淀

用户可将常用命令、脚本模板或错误解决方案保存为技能，也可在远程 `~/hpclaw_skills` 维护个人或课题组知识。后续 Agent 搜索技能时会将这些内容纳入索引。这样，HPClaw 不仅执行任务，也逐步形成面向特定集群和课题组的知识层。

## 13 讨论

HPClaw 展示了一条将生物信息学 AI 助手落到真实 HPC 环境中的路径。它将自然语言交互、集群状态读取、工具执行、技能检索和会话持久化放在同一工作空间中，减少了研究者在聊天工具、终端、文件传输软件和文档之间切换的成本。与纯文本问答相比，HPClaw 更强调真实命令输出和可追溯操作；与传统 Web SSH 相比，HPClaw 增加了领域知识、错误解释和自动化执行；与固定工作流平台相比，HPClaw 更适合探索式、交互式和上下文不断变化的分析任务。

然而，HPClaw 也面临明显挑战。首先，AI Agent 在真实集群中执行命令需要高度谨慎。即便系统禁止部分危险命令，也仍需更严格的权限控制、审计和沙箱策略。其次，生物信息学任务具有高度异质性，软件版本、参考基因组、样本命名和实验设计差异巨大，技能库需要持续维护。第三，系统当前主要围绕单用户 SSH 会话设计，多用户共享、团队协作和管理员审计能力仍需增强。第四，论文层面的定量证据不足，必须通过真实任务、真实用户和跨集群部署补齐。

未来工作包括：将 `server.ts` 拆分为更清晰的后端服务；增强 Agent 计划审批和回滚能力；引入工作流级 provenance 记录并自动生成可复现报告或 notebook；扩展 Slurm/PBS 等调度系统支持；建立更细粒度的远程文件权限和删除保护；构建面向常见生物信息学任务的标准评测集；在多个实验室和集群环境中开展用户研究。

## 14 结论

本文介绍了 HPClaw，一个面向生物信息学 HPC 集群的智能 Web 操作平台。HPClaw 将 Web SSH 终端、AI Agent、远程文件管理、LSF 作业规则、技能知识库、集群状态感知、会话记忆和富内容展示整合在统一界面中，使自然语言请求能够转化为真实集群中的可执行操作。其核心价值在于让 AI 不只回答问题，而是在受控、安全和上下文感知的条件下参与生物信息学分析流程。尽管系统仍需补充严谨评估和生产级安全机制，HPClaw 已经形成了一个可扩展的工程基础，为面向 HPC 的科研智能体和交互式生物信息学工作台提供了实践路径。
